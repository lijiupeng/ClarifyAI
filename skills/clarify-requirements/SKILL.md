# 需求澄清（ClarifyAI）

用户口述需求时通常只说得出主干三五条，剩下的细节由你补全 —— 而你补的很可能不是他要的。
本流程把这些「隐式假设」变成画布上可逐条删改、可裁决的显式条目，在写代码之前就把分歧摊开。

## 何时触发

- 用户提出一个需要实现、但细节不明的需求时 —— **在写第一行代码之前**
- 需求中途变得模糊，你发现自己在「猜」的时候
- 不触发：需求已足够明确、或只是改错别字/调样式这类无需澄清的小改动

## 前置：服务如何启停

ClarifyAI 的 MCP server 随你的进程启停。若希望画布在助手之外（比如你正在等待用户时）也能访问，
建议让它常驻：

```
npx @clarifyai/server --mode=http
```

**当需求已全部收敛、确认不再需要时，可以关闭该服务。** 不要让它一直挂着占端口。

## 流程

### 1. 上报上下文并给出第一层拆解

调用 `clarify_start`，传入项目上下文（技术栈、约定、相关路径）和你对总需求的拆解。

- 凡是你「不确定但先这么假设」的条目，`kind` 一律标成 **`assumption`** —— 这是本工具最核心的价值，用户会专门裁决这些
- 每条都带上 **WHEN/THEN 格式**的验收标准（`WHEN <前置条件> THEN <可观测结果>`）；写不出验收标准，说明这条还没拆到位
- 把用户的原话原样放进 `rawRequirement`，不要改写

### 2. 在编辑器内打开画布，而不是跳系统浏览器

拿到返回的 `uiUrl` 后：

- **VS Code / Cursor**：执行命令 `workbench.action.openSimpleBrowser` 并传入 `uiUrl`
- **JetBrains**：使用内置预览面板（Built-in Preview）
- 其他环境：回落到系统默认浏览器

用户不希望为了确认需求而切出编辑器。

### 3. 轮询阻塞等待裁决（关键，不要跳过）

**循环调用 `clarify_await`，直到用户明确收口为止。**

- 单次 `timeoutMs` 默认用 **25 秒** —— 宿主对工具调用有硬超时，**默认约 60 秒**（实测 59 秒通过、60 秒被掐断）。
  想一次等更久：让用户在宿主的 MCP 配置里给该 server 加 `"timeout"` 字段（CodeBuddy 的 `mcp.json` 实测有效，
  抬到 15 分钟后可单次阻塞 600 秒），同时服务端要用 `--max-block-ms` 把封顶一并放开
- 返回 `status: "pending"` 就**立刻再调一次**，把返回的 `round` 原样传回去当 `sinceRound`
- **重复调用是正常用法，不是出错**。用户的操作不会因为超时而丢失，`round` 游标保证能补回
- 不得因为「等太久了」就中途放弃，也不得跳过澄清直接开工

### 4. 按 `hint` 行动

返回的 `hint` 已经总结了用户做了什么，照着办：

- 有 `userNote`（批注）或 `userFreeText`（自由补充）→ 通过 `replies` **逐条回应**，一条都不能漏
- 有 `expandRequests` → 针对那些节点调用 `clarify_submit_decomposition` 推断新分支
- 仍有 `pendingAssumptions` → 优先处理这些，而不是继续往下拆

**推断子分支时停在需求层面，不要跳到实现细节。** 「用 tsup 打包」「加 bin 字段」这类属于实现，
用户要的是「做什么」而不是「怎么实现」—— 实测中这类条目会被逐条删掉，白占一轮往返。

### 5. 收口

全部裁决后调用 `clarify_finalize`，把返回的 `markdown` 作为实现依据写回你自己的上下文。

`warnings` 非空时先别急着开工：它可能是「仍有待确认的条目被排除在规格之外」——
这些条目**不会**进入规格，看起来却像一切正常。

## 常见误区

- ❌ **把「待确认」当成「已确认」** —— `draft` 状态的条目不会进入规格，静默消失
- ❌ **只调一次 `clarify_await` 就放弃** —— 用户可能只是还在读
- ❌ **在需求层写实现细节** —— 会被用户删掉
- ❌ **跳过澄清直接动手** —— 这正是本工具要消灭的行为
