# 需求澄清（ClarifyAI）

用户口述需求时通常只说得出主干三五条，剩下的细节由你补全 —— 而你补的很可能不是他要的。

本流程把这些「隐式假设」变成画布上一张可逐条删改、可裁决的思维导图，在写代码之前就把分歧摊开。

## 何时触发

- 用户提出一个需要实现、但细节不明的需求时 —— **在写第一行代码之前**
- 需求中途变得模糊，你发现自己在「猜」的时候
- 不触发：需求已足够明确、或只是改错别字/调样式这类无需澄清的小改动

## 前置：服务如何启停

ClarifyAI 的 MCP server 随你的进程启停。若希望画布在助手之外（比如你正在等待用户时）也能访问，
建议让它常驻：

```
npx @clarifyai/server --mode=http
```

**当需求已全部收敛、确认不再需要时，可以关闭该服务。** 不要让它一直挂着占端口。

## 画布是什么样（理解用户视角）

- **单根**：一张画布只有一个根节点，就是这份需求书的标题；所有条目都是它的子孙，没有并列的顶层需求
- **就地编辑**：标题、补充说明直接在卡片里改；`Tab` 加子节点、`Enter` 加同级
- **验收标准只读**：画布上显示成「条件 → 结果」，用户不能手改，只能靠你的建议或重新拆解
- **AI 建议有两种形态**：改内容 / 删节点 / 换父节点 → 灰字挂在目标节点里；
  新增子节点 → 画布上直接出现一张**灰色虚线卡片**，就摆在它会落的位置
- 建议都不算数，用户点「采纳」才变成正式节点 —— 画布上没有「待确认」这种中间状态
- 首页能删除历史会话，删掉就没了

## 流程

### 1. 上报上下文并给出第一层拆解

调用 `clarify_start`，传入项目上下文（技术栈、约定、相关路径）、需求书标题和你对总需求的拆解。

**首轮只搭骨架，不写内容：**

- 只给 `title`，`detail` 和 `acceptance` 一律留空。细节等用户确认结构之后再逐层补
- 首轮缺验收标准是预期内的，服务端会在返回里提示 —— 不要为了消掉这条提示，在第一轮硬凑细节
- 把用户的原话原样放进 `rawRequirement`，不要改写

**结构必须是树，不是清单：**

- `rootTitle` 是整棵树的主干，也就是这份需求书的标题；所有条目都从它延伸出去
- 第一层按**同一个切分维度**展开（功能模块 / 用户旅程 / 系统边界，选一个），兄弟节点之间互斥、合起来覆盖父节点
- 每个子节点都必须能从父节点直接推出来。与父节点无关的内容不要挂进来 —— 要么它属于另一条分支，要么写成 `assumption` 请用户裁决，要么这轮先不写
- 不要把「功能 + 实现细节 + 待办杂项」平铺成一排兄弟节点，也不要把一时想到的零散点直接塞到根下面
- 首轮只挂一层（根的直接子节点），再深的层级等用户提出展开请求时再长
- 凡是你「不确定但先这么假设」的条目，`kind` 标成 **`assumption`** —— 用户会专门裁决这些；它不是「不知道写什么就随便挂一条」的垃圾桶

### 2. 在编辑器内打开画布，而不是跳系统浏览器

拿到返回的 `uiUrl` 后：

- **VS Code / Cursor**：执行命令 `workbench.action.openSimpleBrowser` 并传入 `uiUrl`
- **JetBrains**：使用内置预览面板（Built-in Preview）
- 其他环境：回落到系统默认浏览器

用户不希望为了确认需求而切出编辑器。

### 3. 轮询阻塞等待裁决（关键，不要跳过）

**循环调用 `clarify_await`，直到用户说不用再澄清为止。**

- 单次默认等待 **10 分钟**，通常不用传 `timeoutMs`；宿主对工具调用另有硬超时（不少客户端只有 60 秒），
  要从宿主的 MCP 配置里把该 server 的 `timeout` 一并放大，否则请求会被掐断
- 宿主上限更小时，用服务端 `--max-block-ms` 把封顶压到它以下，让它自己提前返回 `pending` 而不是被杀在半路
- 客户端对同一个 MCP server 的调用是**串行**的：`await` 挂着时调 `clarify_get_session` /
  `clarify_suggest` 会排队，要看状态就先让它返回 `pending`
- 返回 `status: "pending"` 就**立刻再调一次**，把返回的 `round` 原样传回去当 `sinceRound`
- **重复调用是正常用法，不是出错**。用户的操作不会因超时而丢失，`round` 游标保证能补回
- 不得因为「等太久了」就中途放弃，也不得跳过澄清直接开工

### 4. 按 `hint` 行动

返回的 `hint` 已经总结了用户做了什么，照着办：

- 有 `userNote`（批注）或 `userFreeText`（自由补充）→ 通过 `replies` **逐条回应**，一条都不能漏
- 有 `expandRequests` → 针对那些节点调用 `clarify_submit_decomposition` 推断新分支
- 有 `suggestRequests` → 调用 `clarify_suggest`。目标里有根节点 = 整树优化（最多 10 条，可用 `remove` / `move`）；
  目标是普通节点 = 只优化它（最多 3 条）
- 仍有 `pendingAssumptions` → 优先处理这些，而不是继续往下拆

**推断子分支时停在需求层面，不要跳到实现细节。** 「用 tsup 打包」「加 bin 字段」这类属于实现，
用户要的是「做什么」而不是「怎么实现」—— 实测中这类条目会被逐条删掉，白占一轮往返。

### 5. 优化（`clarify_suggest`）

用户点「AI 优化」时：画布上选中了某个节点，就只优化它；没选中，就是优化整棵树。

- 四种动作：`refine` 改内容、`expand` 补子需求、`remove` 删冗余（连同子树）、
  `move` 换父节点并指定顺序（`targetParentId` / `position`）
- 条数由你按内容判断（建议 3~10 条），服务端只挡异常批量，不按场景硬卡
- 用户点「优化整棵树」时，这四件事都可以做：改标题、调顺序（`move`）、
  新增节点（`expand`）、补齐说明与验收（`refine`）；顺手清理真正冗余的 `remove` 也行
- 但**整体意思不能变** —— 不要凭空加用户没提过的功能，也不要把已有条目改写成另一个需求
- 建议**不会**直接改需求树 —— 它以灰字挂在目标节点里，用户逐条「采纳」才生效，忽略就撤掉
- `move` 的 `position` 从 0 起算，表示落到新父节点下的第几位；不传就排到末尾
- 删除不可逆：`remove` 只用来清掉真正冗余的条目，别拿它做「先删后加」的改写
- `note` 写一句为什么这么改，帮用户判断值不值得采纳
- 就算用户没点按钮，每轮也可以主动给少量建议 —— 但别把整棵树重写一遍塞给他，
  那是把裁决成本转嫁出去

### 6. 生成规格快照（不是收口）

需要落地实现时调用 `clarify_finalize`，把返回的 `markdown` 作为实现依据写回你自己的上下文。

- **这不会结束会话**：画布一直可编辑，用户随时能改，需要新快照时再调一次即可
- 没有「收口 / 封板」这种状态，别把它当成一次性的终态
- `warnings` 非空说明这份快照还带着不确定性（比如仍有未裁决的假设），建议先回画布处理

## 常见误区

- ❌ **首轮就把细节铺满** —— 结构还没定，用户要连细节一起改；首轮只给标题
- ❌ **把零散想法直接挂到根下面** —— 与父节点无关的条目不进这棵树，宁可先不写
- ❌ **在第一层混用多种切分维度** —— 兄弟节点必须同质，否则整棵树会歪
- ❌ **只调一次 `clarify_await` 就放弃** —— 用户可能只是还在读
- ❌ **在需求层写实现细节** —— 会被用户删掉
- ❌ **一次提一堆建议** —— 建议 3~10 条；给太多用户一条都不会认真看
- ❌ **整树优化时顺手扩大范围** —— 优化是「把已有的说清楚」，不是「把需求做大」
- ❌ **以为 `clarify_suggest` 改动了需求树** —— 它只产生灰字，用户采纳才落地，别在上下文里当成已确认
- ❌ **跳过澄清直接动手** —— 这正是本工具要消灭的行为
